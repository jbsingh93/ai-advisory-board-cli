# Playwright MCP — reference for the `aab` UI

Authoritative reference for using **Playwright MCP** (the official Microsoft package, `@playwright/mcp`) to drive UI tests of the `aab` web dashboard from inside Claude Code. Read this before writing tests, configuring CI, or installing the MCP on a new machine.

Companion to `PLAN.md` **Part 8**. Status entries live in `PLAN/CHECKLIST.md` **Phase 6.6**.

> **CLI-side counterpart: `PLAN/SMOKE_TESTING.md`.** Same verification discipline for the headless CLI surface — external test folder, real `aab` binary, real Claude calls. Run the relevant one (or both) before declaring a change done. The pairing is: UI changes (`gui/`, `src/gui/server.ts`) → Playwright MCP smoke; CLI changes (the rest of `src/`) → live CLI smoke per `SMOKE_TESTING.md`.

---

## 1. TL;DR — the 60-second version

- **Server**: `@playwright/mcp` (Microsoft / official, pinned to `0.0.75`). The community `@executeautomation/playwright-mcp-server` is **not** used.
- **Install method**: project-scoped — committed `.mcp.json` at repo root, server installed as devDep so teammates inherit it on `npm install`. Cross-platform (Windows-safe; avoids the `npx` stdio pipe bug).
- **Required one-time setup**: `npm install` then `npx playwright install` (downloads browser binaries — ~500 MB).
- **Default mode**: accessibility-tree snapshots (not screenshots). The model targets elements by ref tokens like `ref=e5` returned in the snapshot — small payloads, no vision model needed.
- **Two-track testing**:
  - **Playwright MCP** — exploration, ad-hoc verification, test authoring, flake repro from inside Claude Code.
  - **`@playwright/test`** *(future)* — the deterministic regression suite that runs in CI. Generated by MCP, committed to `tests/`, executed without an LLM.
- **`/mcp` inside Claude Code** lists active servers. First time you run Claude Code in this repo, you'll be prompted to approve `playwright` from `.mcp.json` — this is by design.

## 2. Why we chose this

The `aab` web dashboard at `gui/` is the right test surface — vanilla JS, no build step, drives the same engine (`src/core/discussion/conversation-flow.ts`) the CLI does, exposes a live WebSocket event stream. Black-box UI testing is the only way to verify: typing-dot animations, structured response cards rendering, HITL panels appearing on `request_user_input`, the Continue/Follow-up/Respond buttons firing the right REST endpoints, the multi-round flow surviving cross-WS reconnects.

Why **Playwright MCP** specifically over alternatives:

- **Official Microsoft package**, listed as canonical on [playwright.dev/docs/getting-started-mcp](https://playwright.dev/docs/getting-started-mcp), 32k+ stars, 65+ releases as of May 2026.
- **Accessibility-tree-first architecture** — the model sees a structured tree (roles, names, refs), not screenshots. Cheap, deterministic, robust to CSS changes, no vision-capable model required.
- **Claude Code-native** — installs via standard `claude mcp add` or `.mcp.json`; teammates get the same server on `git pull`.
- **Larger capability surface** than the community fork (PDF, tracing, network mocking, storage CRUD, structured testing verifiers — see §5).

Why **not** the community package (`@executeautomation/playwright-mcp-server`): unofficial, smaller surface for agent-driven flows, marketed for codegen/scraping. Its only standout — 143 device emulation presets — is matched by `@playwright/mcp --device "iPhone 15"` etc.

Why **not** just Playwright CLI via the Bash tool: lower token cost per turn (CLI ~27k vs MCP ~114k for a representative session per [testdino.com](https://testdino.com/blog/playwright-mcp)), but no persistent browser state between turns, no a11y-tree introspection, no interactive login flows. For *interactive exploration* MCP wins; for *batch test execution* the standard `@playwright/test` runner via Bash is better. See §8.

## 3. Setup

### One-time, per developer

```bash
# 1. From the repo root, pulled and `npm install` is already done
npm install                                # installs @playwright/mcp@0.0.75 as devDep

# 2. Install the actual browser binaries (Playwright ships Node bindings only)
npx playwright install                     # downloads Chromium/Firefox/WebKit (~500MB)
# Linux/Docker only — also install OS libs:
# npx playwright install-deps

# 3. Optionally pre-verify the MCP server starts (no Claude Code needed)
node node_modules/@playwright/mcp/cli.js --help | head -20

# 4. First time you open this repo in Claude Code, it asks for permission to start
#    the project-scoped server. Approve once. Reset later with:
#    claude mcp reset-project-choices
```

### What's committed

| File | Purpose |
|------|---------|
| `.mcp.json` | Project-scoped MCP server config (Microsoft Playwright MCP). Cross-platform — uses `node node_modules/.../cli.js` not `npx`. |
| `package.json` | `@playwright/mcp` pinned in `devDependencies`. |
| `PLAN/PLAYWRIGHT_MCP.md` | This file. |

### What is *not* committed

- `test-artifacts/playwright-mcp/` — screenshots, videos, traces emitted by MCP runs. **Add to `.gitignore`** the first time the directory is populated.
- The browser binaries — they live under `~/.cache/ms-playwright/` (Linux/macOS) or `%USERPROFILE%\AppData\Local\ms-playwright\` (Windows).

### Verifying it works inside Claude Code

In a Claude Code session in this repo:

1. Type `/mcp` — you should see `playwright` listed.
2. Ask Claude: "Use the Playwright MCP to navigate to https://example.com and take a snapshot." Expect to see a `browser_navigate` then `browser_snapshot` tool call.

### What's pinned in `.mcp.json` and why

```json
{
  "$schema": "https://json.schemastore.org/mcp.json",
  "mcpServers": {
    "playwright": {
      "type": "stdio",
      "command": "node",
      "args": [
        "node_modules/@playwright/mcp/cli.js",
        "--browser", "chromium",
        "--viewport-size", "1280x800",
        "--caps", "core,testing,storage,devtools",
        "--allowed-origins", "http://localhost:*;http://127.0.0.1:*",
        "--output-dir", "test-artifacts/playwright-mcp",
        "--test-id-attribute", "data-testid",
        "--timeout-navigation", "15000"
      ]
    }
  }
}
```

Rationale for each flag:

- `command: node` + direct path to `cli.js`: bypasses the **Windows + `npx` stdio bug** (see §11). Works identically on macOS/Linux. The path is project-relative, so it resolves from any teammate's clone.
- `--browser chromium`: matches what `aab ui` will be tested against. Add `firefox`/`webkit` for cross-browser regression when we get there.
- `--viewport-size 1280x800`: the dashboard's design target. Pair with a `375x667` mobile run in dedicated tests when we test mobile.
- `--caps core,testing,storage,devtools`: enables the assertion verifiers (`browser_verify_*`), storage CRUD for seeded auth state, and tracing for flake diagnosis. **`vision` and `network` are intentionally omitted** to reduce token surface and tool-search noise — re-enable per-session if needed.
- `--allowed-origins http://localhost:*;http://127.0.0.1:*`: hard fence — the MCP cannot navigate to the public internet from this server. Defensive against accidental data exfil via the model.
- `--output-dir test-artifacts/playwright-mcp`: all screenshots/videos/traces land here. Gitignore the directory.
- `--test-id-attribute data-testid`: the locator convention we'll use in `gui/index.html` (`<button data-testid="discussion-continue">…</button>`). Standard, matches `@playwright/test` defaults.
- `--timeout-navigation 15000`: Claude calls + WS round-trips can take 5-10 s; default 60 s is too generous (masks real flakes), default 5 s would false-fail.

**Not** in the config (deliberately):

- `--headless` — kept off. We want a visible browser during dev, both for human observation and to let users complete OAuth/MFA flows manually if needed. Override with `--headless` in CI.
- `--isolated` — kept off. Persistent profile means cookies + workspace state survive between MCP calls in a session, which makes exploratory testing snappier. Pair with `--storage-state` in CI.
- `--save-trace` — kept off in default config because most exploratory sessions don't need it. Turn on per-session when reproducing a hard flake.

## 4. Snapshot mode vs vision mode

**Default: snapshot mode (accessibility tree).** Every interactive call returns a structured tree like:

```
- button "Start discussion" [ref=e5]
- textbox "Question" [ref=e7] focused
- text "3 active members" [ref=e9]
```

The model then issues `browser_click({ ref: "e5" })`. No selectors, no pixels.

**Vision mode (`--caps=vision`)**: enables `browser_mouse_*_xy` tools acting on pixel coordinates. Returns screenshots. **Only enable when:**

- The UI uses `<canvas>` / `<svg>` you need to interact with (whiteboards, charts, draggable diagrams).
- Elements aren't exposed in the accessibility tree (custom drag handles, fully decorative UI).
- You're specifically testing visual layout.

For `aab`'s vanilla-HTML dashboard, **snapshot mode is sufficient for everything**. If a button isn't clickable via a11y ref, **fix the markup** — add the missing `aria-label` or `data-testid` — don't escalate to vision mode. This is the same hygiene that pays off for screen-reader users.

To enable vision per session (don't commit this):

```bash
# Override --caps for a one-off
node node_modules/@playwright/mcp/cli.js --caps core,testing,vision
```

## 6. Repo conventions for testable UI

Playwright MCP works best when the dashboard cooperates. As we build out the UI, follow these conventions so MCP-driven tests stay stable across CSS refactors.

### Locator priority (highest first)

1. **`data-testid`** — opaque, never changes for styling reasons. Use for primary interactive elements: `discussion-start`, `discussion-continue`, `discussion-respond`, `discussion-follow-up`, `member-chip-{slug}`, `hitl-option-{index}`, `tab-{name}`.
2. **`role` + accessible name** — `button "Start discussion"`, `textbox "Question"`. Free if you write semantic HTML.
3. **Visible text** — `button:has-text("Start")`. Fragile to copy changes.
4. **CSS classes / structural selectors** — **avoid** for tests. Fine for styling, brittle for assertions.

### Required `data-testid`s for current UI surface

These should exist on the elements they describe; add when missing as part of the UI test setup:

| Element | testid |
|---------|--------|
| Sidebar tab buttons | `tab-discussions`, `tab-action-board`, `tab-members`, `tab-principles`, `tab-settings`, `tab-knowledge` *(when Phase 1.5 ships)* |
| New-discussion button | `new-discussion` |
| New-discussion modal question textarea | `new-discussion-question` |
| New-discussion modal member toggle | `new-discussion-member-{slug}` |
| New-discussion modal start button | `new-discussion-start` |
| Discussion list row | `discussion-row-{shortId}` |
| Chat view continue button | `discussion-continue` |
| Chat view follow-up open button | `discussion-followup-open` |
| Chat view follow-up composer | `discussion-followup-input` |
| Chat view follow-up send | `discussion-followup-send` |
| Chat view HITL option button | `hitl-option-{index}` |
| Chat view HITL reply textarea | `hitl-reply-input` |
| Chat view HITL submit | `hitl-reply-submit` |
| Per-member typing-dot bubble | `member-typing-{slug}` |
| Per-member message bubble | `member-message-{slug}-{turnNumber}` |
| Orchestrator decision card | `orchestrator-decision-{roundNumber}` |
| Discussion concluded marker | `discussion-concluded` |

These are codified so any agent author can scan the list, then write the markup. Future UI changes should keep these stable even if classnames/positions move.

### Accessibility hygiene

- Every interactive element needs a visible label or `aria-label`. The a11y tree shows nothing for unlabeled buttons.
- Decorative icons → `aria-hidden="true"`.
- Live regions for the typing-dot bubble and orchestrator decisions → `role="status"` `aria-live="polite"` so MCP sees them appear/disappear.
- The HITL reply panel → `role="dialog"` `aria-modal="true"` so the model can tell it's the focus.

### WebSocket synchronization

The dashboard's hot path is WS-driven. Tests must wait on **observable UI changes** (snapshot diffs), not arbitrary timeouts:

- ✅ `browser_wait_for({ text: "Round 2" })` after clicking Continue
- ✅ `browser_wait_for({ ref: "member-message-elon-musk-2" })` after expecting a response
- ❌ `sleep(5000)` — never. If we can't observe the change, the dashboard needs a `data-testid` or `aria-live` region added.

## 7. How to drive tests from Claude Code

This section is the prompt cookbook. The patterns below have been validated by the community (see [alexop.dev](https://alexop.dev/posts/building_ai_qa_engineer_claude_code_playwright/), [testdino.com](https://testdino.com/blog/playwright-mcp)) and adapted to `aab`'s surface.

### Pattern A — exploratory smoke test

Use during dev to sanity-check that a recent change didn't break the basics.

```
You are testing the aab web dashboard at http://localhost:3737 via Playwright MCP.

Rules:
- UI ONLY. Interact through the browser like a real user. Don't read source code unless I ask.
- Use data-testid locators first, then role+name, never CSS classes.
- After each significant step, take a snapshot.
- On any unexpected state, take a screenshot, document the bug in 1-2 sentences, KEEP TESTING.
- Don't sleep. Use browser_wait_for on visible text or testids.
- Test mobile last (resize to 375x667).

Smoke flow:
1. Navigate to /. Verify the sidebar lists the 5 tabs and Discussions is selected.
2. Open the new-discussion modal. Verify all active members appear as toggleable chips.
3. Start a discussion with the question "Should we ship the wiki phase 1 chunk 1 first or finish phase 1 closeout?"
4. Wait for the round-1 typing bubbles to appear, then for the first member message.
5. If the orchestrator gates with a HITL panel, document the question + options and STOP. Do not respond.
6. If round 1 completes without HITL, click Continue, then wait for round 2.

Report bugs as a markdown table: location, what happened, what should have happened, screenshot path.
```

### Pattern B — regression repro

Use when CHANGELOG.md describes a bug fix and you want to verify the fix holds.

```
The fix from 2026-05-10 was: when a discussion concludes via maxTurns, leftover
pendingUserRequest is cleared so the UI never shows "done" alongside an unanswerable
HITL prompt.

Reproduce the precondition: start a discussion, drive rounds until maxTurns
(currently 10 per default settings) is reached. After conclusion, verify that:
- The chat view shows "discussion-concluded".
- No HITL reply form is visible.
- The Continue button is not visible (or visibly disabled).

Take screenshots at the moment of conclusion. If any HITL prompt remains visible,
this regression is back — print the failing state in red.
```

### Pattern C — generate a `@playwright/test` spec from exploration

When you've explored a flow that should be in CI, ask Claude to write it out.

```
Now generate a Playwright @playwright/test spec file at tests/e2e/discussion-happy-path.spec.ts
that reproduces what you just did. Requirements:
- import { test, expect } from '@playwright/test'
- Use page.getByTestId() for every locator
- Use expect(...).toBeVisible(), .toHaveText(), .toHaveValue() for assertions — no manual waits
- One test per logical assertion (don't pile 10 verifications into one `test()`)
- Skip the discussion-creation step if it takes >30 s; use a fixture instead (we'll wire that up later)
- Add a top-of-file comment explaining what flow this covers

Output the file content only, no commentary.
```

### Pattern D — accessibility audit

```
Audit http://localhost:3737 for accessibility issues. For each tab in the sidebar:
1. Navigate, take a snapshot.
2. List every interactive element that lacks a visible label or aria-label.
3. List every image without alt text.
4. List every form input without an associated label.
5. Report keyboard-trap or focus-order problems if any.

Output: a table per tab. End with a summary of the top 3 highest-impact fixes.
```

### Anti-patterns to avoid

- ❌ **"Test the dashboard."** — too vague; produces inconsistent runs.
- ❌ **Telling the model to "wait 5 seconds before clicking"** — leads to flake. Always wait on an observable state change.
- ❌ **Letting the model use `browser_run_code_unsafe`** — RCE-equivalent, deny in permissions.
- ❌ **Asking the model to inspect source files first** — defeats the point of black-box UI testing.
- ❌ **Committing test runs to git** — `test-artifacts/` is `.gitignore`-d for a reason; screenshots can contain real Claude responses.

## 8. When MCP, when `@playwright/test`

The split is well-established in the 2026 community consensus. Treat it as policy.

| Use case | Tool |
|----------|------|
| "What's on this page?" | **MCP** |
| Reproducing a flaky bug interactively | **MCP** |
| Drafting a first test for a new flow | **MCP** (then commit as `.spec.ts`) |
| Ad-hoc a11y audit during dev | **MCP** |
| Updating selectors after a UI refactor | **MCP** (regenerate, commit) |
| The regression suite running on every PR | **`@playwright/test`** |
| Cross-browser sharded execution | **`@playwright/test`** |
| Visual regression diffs | **`@playwright/test` + `toHaveScreenshot()`** |
| Hermetic tests that mock the `claude` CLI | **`@playwright/test`** (with msw or Playwright's `page.route`) |

**Why the split:**
- MCP burns ~3-4× the tokens per generated test compared to direct CLI use ([betterstack.com](https://betterstack.com/community/guides/ai/playwright-cli-vs-mcp-browser/), [testdino.com](https://testdino.com/blog/playwright-mcp)). Fine for exploration; wasteful for re-running 200 tests.
- MCP doesn't run headless cleanly in CI (works, but not the design center). `@playwright/test` was built for it.
- AI-generated test code needs human review before it's CI-worthy. MCP is the **author**, `@playwright/test` is the **runner**.

**Project structure once `@playwright/test` lands (future Phase 6.6+):**

```
tests/
  e2e/
    discussion-happy-path.spec.ts
    discussion-hitl-flow.spec.ts
    discussion-follow-up.spec.ts
    members-tab.spec.ts
    a11y/
      sidebar.spec.ts
  fixtures/
    seeded-workspace.ts       # creates a tempdir workspace with starter members
    mock-claude.ts            # stubs the `claude` binary for hermetic tests
  e2e.config.ts               # standard @playwright/test config
test-artifacts/
  playwright-mcp/             # MCP runtime output (gitignored)
  playwright-test/            # CI runner output (gitignored)
.mcp.json                     # committed (this repo)
playwright.config.ts          # added when @playwright/test is installed (future)
```

## 9. Configuration deep-dive

For one-off overrides (don't commit). Pass via the JSON config option:

```bash
node node_modules/@playwright/mcp/cli.js --config '{"snapshot":{"mode":"none"},"imageResponses":"omit"}'
```

Full schema, from the [Microsoft README](https://github.com/microsoft/playwright-mcp):

```typescript
{
  browser?: {
    browserName?: 'chromium' | 'firefox' | 'webkit';
    isolated?: boolean;
    userDataDir?: string;
    launchOptions?: playwright.LaunchOptions;
    contextOptions?: playwright.BrowserContextOptions;
    cdpEndpoint?: string;
    cdpHeaders?: Record<string, string>;
    cdpTimeout?: number;
    remoteEndpoint?: string;
    initPage?: string[];                // URLs to navigate on launch
    initScript?: string[];              // JS to inject on launch
  };
  extension?: boolean;
  server?: { port?: number; host?: string; allowedHosts?: string[] };
  capabilities?: ToolCapability[];      // 'core','pdf','devtools','vision','network','storage','testing','config'
  saveSession?: boolean;
  sharedBrowserContext?: boolean;
  secrets?: Record<string, string>;
  outputDir?: string;
  console?: { level?: 'error' | 'warning' | 'info' | 'debug' };
  network?: { allowedOrigins?: string[]; blockedOrigins?: string[] };
  testIdAttribute?: string;
  timeouts?: { action?: number; navigation?: number; expect?: number };
  imageResponses?: 'allow' | 'omit';
  snapshot?: { mode?: 'full' | 'none' };
  allowUnrestrictedFileAccess?: boolean;
  codegen?: 'typescript' | 'none';
}
```

### Useful CLI flags not in our committed config

| Flag | When you'd use it |
|------|-------------------|
| `--headless` | CI runs |
| `--isolated` | When you want a fresh profile every session (e.g. testing first-time onboarding) |
| `--storage-state path/to/state.json` | Seed a logged-in or pre-configured browser |
| `--device "iPhone 15"` | Mobile emulation with one preset |
| `--no-sandbox` | Docker/CI on Linux |
| `--init-page http://localhost:3737` | Auto-navigate to the dashboard on launch |
| `--save-trace` | Persist a Playwright trace for offline inspection |
| `--proxy-server http://...` | Corporate-network testing |
| `--ignore-https-errors` | Local dev with self-signed certs (we don't use HTTPS locally, so usually moot) |

### Capability-flag costs

Every enabled capability adds tools to the MCP schema, which Claude Code loads upfront. **Tool Search** (default-on in Claude Code 2026+) defers individual tool schemas until needed, so the overhead is mostly the *names*, not the *full definitions*. Still, don't enable capabilities you don't use — keeps `/mcp` output clean and Tool Search results sharper.

### MCP output token cap

Claude Code caps MCP responses at 25,000 tokens by default (warning at 10,000). A11y snapshots of dense pages can push this. Two mitigations:

- `imageResponses: 'omit'` in config — don't return screenshot bytes to the model when you don't need them.
- `export MAX_MCP_OUTPUT_TOKENS=50000` before starting Claude Code — bump the cap.

Source: [Claude Code MCP docs § Output limits](https://code.claude.com/docs/en/mcp).

## 10. Troubleshooting

| Symptom | Likely cause | Fix |
|---------|--------------|-----|
| `/mcp` shows playwright as "failed" or with 0 tools | Browser binaries missing | `npx playwright install` |
| `/mcp` shows playwright but every tool call times out | Often Windows + npx (we already avoided this in `.mcp.json`); occasionally browser path mismatch | Verify with `node node_modules/@playwright/mcp/cli.js --help` directly in a shell |
| "TimeoutError: navigation timeout of 60000 ms exceeded" | Slow page load (often `aab ui` boot lag) | Bump `--timeout-navigation` or start the dashboard first |
| Snapshot says element "not exposed in accessibility tree" | Missing `aria-label`, `aria-hidden` on wrapper, or hidden by CSS | Fix the markup, not the test |
| Model picks weird selectors that drift between runs | Underspecified prompt — see anti-patterns | Add explicit `data-testid` and instruct the model to prefer it |
| MCP returns 25k-token cap error on snapshot | Page has too much content | `imageResponses: 'omit'` or bump `MAX_MCP_OUTPUT_TOKENS` |
| `browser_run_code_unsafe` shows up in a session and you didn't ask for it | Model improvised | Deny it in `.claude/settings.json` permissions |
| Permission prompt re-appears on every start | Per-project approvals got cleared | Approve once; `claude mcp reset-project-choices` only if you want to re-prompt |
| Persistent profile conflicts between two Claude Code sessions | Both spawned playwright MCP, locked on same `user-data-dir` | Add `--isolated` to one session |
| Server hangs silently with no logs | Check `~/Library/Logs/Claude/mcp-server-playwright.log` (macOS) or `%USERPROFILE%\AppData\Roaming\Claude\logs\` (Windows) | Launch `node node_modules/@playwright/mcp/cli.js` directly in a shell to see stderr |

### Verification handshake (Windows)

If MCP appears completely silent on Windows, sanity-check the server starts and responds to JSON-RPC:

```powershell
echo '{"jsonrpc":"2.0","id":1,"method":"initialize","params":{"capabilities":{}}}' | node node_modules/@playwright/mcp/cli.js
```

Should print a JSON-RPC response with the server name + version. If it hangs, the server itself is broken — file an issue at [microsoft/playwright-mcp](https://github.com/microsoft/playwright-mcp/issues).

## 11. Windows notes

**The bug we deliberately avoided**: `@playwright/mcp` started via `npx` on Windows has been broken since at least version 0.0.41 (still open as of 0.0.68+ per [Issue #1540](https://github.com/microsoft/playwright-mcp/issues/1540)). Symptom: server "starts" but Claude Code never sees any tools / hangs silently. Root cause: `npx` is `npx.cmd`, which when spawned via `cmd.exe /c` doesn't properly connect stdin/stdout pipes to the underlying Node process.

**Our fix**: `.mcp.json` uses `command: "node"` with a direct path to `cli.js`. Works identically on macOS/Linux. Don't "fix" it back to `npx` — you'll re-introduce the bug for every Windows teammate.

**Other Windows-specific gotchas:**

- Browser binaries land under `%USERPROFILE%\AppData\Local\ms-playwright\` — sometimes blocked by corporate AV. If `npx playwright install` succeeds but the browser won't launch, check Defender / corporate AV exclusions.
- PowerShell single quotes around JSON don't interpolate — use `@'...'@` here-strings if you need multi-line JSON in a CLI call.
- File paths in `.mcp.json` use forward slashes (`node_modules/.../cli.js`) and work on all platforms. Don't switch to backslashes for Windows; JSON would require escaping and you'd break macOS/Linux.

## 12. Security

### `browser_run_code_unsafe`

The most dangerous tool in the surface. From the Microsoft README, verbatim:

> Unsafe: executes arbitrary JavaScript in the Playwright server process and is RCE-equivalent — only enable it for trusted MCP clients.

It ships in `core` and cannot be selectively disabled via `--caps`. If you don't trust the prompt source (or just want defense-in-depth), deny it explicitly in `.claude/settings.json`:

```json
{
  "permissions": {
    "deny": [
      "mcp__playwright__browser_run_code_unsafe"
    ]
  }
}
```

(Tool names in deny lists follow the `mcp__<server>__<tool>` pattern in Claude Code permissions.)

### Origin allowlist

We pin `--allowed-origins http://localhost:*;http://127.0.0.1:*`. The MCP cannot navigate outside this list, so an injected prompt can't make the browser hit attacker-controlled URLs. **Don't add the public internet** to this list. If you genuinely need to test external resources (rare), do it in a one-off session with an explicit override, not in `.mcp.json`.

### Output dir

Screenshots and traces can contain real Claude responses (in our case: full advisory-board discussions). Keep `test-artifacts/playwright-mcp/` gitignored, and don't paste full traces into public issues.

### Persistent profile

The default persistent profile stores cookies/localStorage between sessions, hashed by workspace path. Useful for keeping a logged-in state during exploratory testing — but it persists *whatever* the model navigated to. If a test session navigated to a sensitive internal URL (it shouldn't, given the origin allowlist), that history sticks. Wipe with `--isolated` runs when in doubt.

## 13. CI guidance (placeholder — Phase 6.6+)

Not built yet, but the design intent is:

1. **GitHub Actions matrix**: Node 20 + 22, ubuntu-latest + windows-latest + macos-latest.
2. **CI uses `@playwright/test`**, not MCP. MCP is for the dev loop.
3. **`aab ui` dev server** spawned by a Playwright test fixture pointing at a tempdir workspace seeded by `aab init`.
4. **Mocked `claude` binary** so tests don't consume real subscription tokens — point `PATH` at a stub that returns canned JSON envelopes.
5. **Test sharding** with `--shard 1/4` etc.
6. **Failure artifacts** (trace + screenshot + video) uploaded as GitHub Actions artifacts.
7. **Visual regression** with `expect(page).toHaveScreenshot()` — accept baseline diffs only via deliberate `--update-snapshots` PRs.

See [Playwright docs § CI](https://playwright.dev/docs/ci) when wiring this up.
