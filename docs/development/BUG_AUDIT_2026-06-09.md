## Fixed

### M1 — `startDiscussion` aborted the whole round on one member failure
`src/core/discussion/conversation-flow.ts` (round-1 loop). The loop had no
per-member try/catch, so a single flaky member killed the entire discussion and
wasted every prior member's tokens; the "All board members failed to respond"
check below it was unreachable dead code. Now wrapped exactly like
`continueDiscussion`'s tolerant loop (`logger.warn`, continue with the others);
the all-failed check is live. Commit `c94cef9`.

### M3 — follow-up pre-round gate silently dropped a `conclude` decision
`src/core/discussion/conversation-flow.ts` (`addFollowUpQuestion`). The gate
handled only `request_user_input`; a `conclude` decision fell through and the
round ran anyway. Confirmed with the user as a bug. Now mirrors
`continueDiscussion`: marks `completedAt`, stamps the decision on the most
recent round, saves, returns `{ concluded: true }`. Commit `c94cef9`.

### M5 — HITL reply attached to the new round with the previous round's number
`src/core/discussion/conversation-flow.ts` (`continueDiscussion` +
`respondToUserRequest`). `round.userResponse` reused the entry stamped with the
*previous* round's number, so round N+1 carried a userResponse claiming round N.
Now attached as a copy re-stamped with the round it actually drives; the entry
in `discussion.userResponses` is not mutated. Commit `c94cef9`.

### M2 — double-submit race on discussion mutation endpoints
`src/gui/server.ts`. `/api/discussions/:id/{continue,respond,follow-up}` return
202 and run the round async; two rapid submits loaded the same discussion
record twice and the second save clobbered the first round (last-writer-wins).
Added an in-flight `Set<discussionId>` (same idea as the existing
`runningPlans` map): check+add happens synchronously so concurrent requests
can't both pass; second request gets 409; the id is released in `.finally`.
`POST /api/discussions` (new discussion) was deliberately **not** guarded — two
clicks there create two independent records, no shared state to corrupt.
Commit `24ab033`.

**Live verification (2026-06-09T18:12–18:14Z):** built `aab ui` served against a
throwaway home workspace seeded with one member + one open discussion, with a
fake `claude` shim on PATH that sleeps 6 s (keeps a round in flight; no real
LLM calls). Results:
- request 1: `HTTP 202 {"accepted":true}`
- request 2 (0.3 s later, round still running): `HTTP 409 {"error":"A round is already running for this discussion."}`
- after the round failed (fake claude exits 1; server log shows one `continue failed`): request 3 → `HTTP 202` — guard correctly released by `.finally` even on failure.
Server stopped and workspace/shim/logs deleted afterwards.

### M4 — business-context writes had no snapshot history
`src/storage/fs-storage-service.ts`. `saveBusinessContext` /
`updateBusinessContext` / `deleteBusinessContext` were the only persistent-entity
writes not passing `{ snapshotDir }` (settings/members/principles/boards/profile
all do), so a corrupted write was unrecoverable. All three now snapshot before
overwrite. Commit `2aab3d6`.

### L1 — bare `Error` where `UserError` belongs
`conversation-flow.ts` (no-active-members, all-members-failed in
`startDiscussion`) and `fs-storage-service.ts` (duplicate-member id, all six
board-validation throws). Messages are user-facing; bare `Error` skipped the
`✗` + hint formatting in `handleError`. Message texts unchanged — only the
class. Commits `c94cef9`, `2aab3d6`.

### L5 — start-discussion failure broadcast had no correlation
`src/gui/server.ts`. The async-failure WS broadcast for `POST /api/discussions`
now carries `context: 'start_discussion'` so clients can tell it apart from a
round failure on an existing discussion (no discussion id exists yet at that
point). The frontend already toasts every `{type:'error'}`, so no frontend
change was needed. Commit `24ab033`.

### L2 — unreadable agent files were treated as overwritable
`src/agents/emit-member-agent.ts`. `isAabGenerated()` returned `true` (safe to
overwrite) when an *existing* file couldn't be read (permissions, transient FS
error), so a hand-edited file could be clobbered by `sync-agents` during a
blip. The catch now returns `false`; missing files still return `true`
(unchanged `existsSync` path). Commit `ecbf00f`.

### L3 — doctor printed hardcoded Windows separators
`src/commands/doctor.ts`. The agents-dir detail interpolated literal `\.claude\agents\`;
now `join(projectRoot, '.claude', 'agents')`. Commit `ecbf00f`.

## Documented only — NO code change (user direction)

### H1 — wiki renderer injects body text as raw HTML
`gui/wikilinks.js` `renderWikiBody()`/`inlineFormat()`: plain-text lines and the
bold/italic `$1` captures reach `innerHTML` unescaped, so HTML in a wiki page
body renders/executes in the dashboard. The user confirmed the wiki
intentionally renders content as-is (local-only app, user's own content) — left
exactly as it is.

### L4 — wiki raw-file endpoint trusts manifest paths
`GET /api/knowledge/raw/:hash` serves `join(workspaceRoot, entry.rawPath)`
without a containment check. Manifest is server-written and the server binds
localhost; the user declined folder restrictions on wiki file serving — left
exactly as it is.

## Investigated and ruled out (false positives)

- **"`pendingUserRequest` not cleared on the maxTurns early-returns"**
  (`continueDiscussion` / `addFollowUpQuestion`): unreachable — both functions
  throw earlier when `pendingUserRequest` is set, and `respondToUserRequest`
  clears + persists it before re-entering `continueDiscussion`. The documented
  invariant is correctly implemented in the post-round conclude path.
- **"Gated-discussion footer renders stale state"** (`gui/app.js`
  `finalizeChat`): the footer is already rendered from the authoritative
  `msg.discussion`; the async `/api/state` fetch only refreshes list data and
  triggers no re-render. No change.
- Lock release on command error paths (try/finally everywhere), workspace
  resolution order, atomic tmp+rename writes, member short-ID min-length —
  all verified correct or intentional.
